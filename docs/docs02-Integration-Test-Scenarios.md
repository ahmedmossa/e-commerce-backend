## 2. سيناريوهات الاختبار الأساسية (Core Test Scenarios)

### 🔹 السيناريو الأول: دورة التسجيل، المصادقة، والـ OTP
* **صاحب التراك:** م. أحمد سمير مصطفى مخيمر (تراك 02)
* **مسار الـ API:** `POST /api/v1/auth/signup` -> `POST /api/v1/auth/verify-otp`
* **خطوات التنفيذ:**
  1. إرسال بيانات المستخدم الجديد إلى مسار التسجيل (`signup`).
  2. التحقق من توليد كود الـ OTP وتخزينه مشفراً، وإرسال البريد بنجاح عبر خدمة `sendEmail.js`.
  3. إرسال الـ OTP للتحقق والتأكد من تفعيل الحساب وإرجاع رمز الـ `JWT Token`.

### 🔹 السيناريو الثاني: دورة سلة الشراء والمخزون اللحظي (Cart Flow)
* **صاحب التراك:** م. رحمة محمود شعيب (تراك 06)
* **مسار الـ API:** `POST /api/v1/cart` -> `POST /api/v1/cart/apply-coupon`
* **خطوات التنفيذ:**
  1. إضافة منتج للسلة مع تحديد الكمية بدقة (`POST /api/v1/cart`).
  2. التحقق من حساب المجموع الكلي (Total Price) ديناميكياً باستخدام خصائص Mongoose Virtuals، والتحقق من عدم تجاوز المخزون المتاح.
  3. تجربة تطبيق كوبون خصم صالح (`apply-coupon`) والتحقق من تحديث السعر النهائي.

### 🔹 السيناريو الثالث: دورة الطلب والدفع الإلكتروني (Order & Stripe Payment)
* **أصحاب التراك:** م. عمر أشرف (تراك 08) + م. ديما سامح (تراك 09)
* **مسار الـ API:** `POST /api/v1/orders` -> `POST /api/v1/payment/create-payment-intent`
* **خطوات التنفيذ:**
  1. إنشاء طلب جديد من محتويات السلة (`POST /api/v1/orders`).
  2. التحقق من استخدام معاملات قاعدة البيانات (`Mongoose Transactions`) لضمان حجز المخزون وعدم حدوث خصم مزدوج.
  3. استدعاء مسار الدفع عبر Stripe والتأكد من استجابة الـ Webhook بنجاح وتحديث حالة الطلب إلى `Paid`.
  4. **حالة الإلغاء:** عند إلغاء الطلب، التأكد من استرجاع المخزون مرة واحدة بدقة.

## 3. اختبارات التزامن والحالات الخاصة (Concurrency & Edge Cases)

* **اختبار تزامن الشراء (Last Item Concurrency):**
  * *الوصف:* محاكاة مستخدمين يحاولان شراء آخر قطعة مخزون متبقية لنفس المنتج في نفس اللحظة الزمنية بالضبط[cite: 1].
  * *النتيجة المتوقعة:* نجاح معاملة واحدة فقط بفضل القيود الذرية لقاعدة البيانات، وفشل المعاملة الأخرى مع رسالة توضح نفاد المنتج[cite: 1].

* **اختبار منع تكرار أحداث الدفع (Webhook Idempotency):**
  * *الوصف:* إرسال نفس إشعار الدفع الإلكتروني (`Stripe Webhook`) مرتين بالخطأ[cite: 1, 8].
  * *النتيجة المتوقعة:* معالجة الحدث المالي مرة واحدة فقط وتجاهل التكرار لمنع أي تضارب في السجلات المالية[cite: 1, 7, 8].

## 4. نموذج تقرير الأخطاء (Bug Report Template)
عند اكتشاف أي خطأ أثناء اختبارات التكامل، يتم تسجيله بالنموذج التالي:

- **Bug ID:** BUG-00X
- **Module / Track:** [مثلاً: Cart / Order / Auth]
- **Severity (الخطورة):** [Critical / High / Medium / Low]
- **Description (الوصف):** ملخص واضح للسلوك غير المتوقع.
- **Steps to Reproduce (خطوات إعادة الإنشاء):**
  1. الخطوة الأولى...
  2. الخطوة الثانية...
- **Expected Result (النتيجة المتوقعة):** ما كان يجب أن يحدث بناءً على عقد الـ API.
- **Actual Result (النتيجة الفعليّة):** ما حدث بالفعل (مع إرفاق رمز الاستجابة والخطأ البرمجي).
